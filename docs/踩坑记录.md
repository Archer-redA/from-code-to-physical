## 坑 1：`git push` 到 Gitee 一直被拒绝（Permission denied）

**这是本次卡得最久的一个问题。**

### 现象

配置好 Gitee 远程仓库后推送，被直接拒绝：

```console
$ ssh -T git@gitee.com
git@gitee.com: Permission denied (publickey).
```

连不上就是连不上，没有提示「你是哪个用户」，也没有任何引导。
这句话看上去像是网络不通，很容易让人以为是代理或者防火墙的问题。

### 排查过程

一开始的方向是错的 —— 因为「拒绝访问」这四个字太像网络故障了，所以先去查网络：

1. 检查 HTTPS 能不能通：
   ```console
   $ git ls-remote https://gitee.com/oschina/git-osc.git HEAD
   ```
   能正常返回结果 → **说明网络是通的**，Gitee 服务器访问得到，问题不在网络上。

2. 既然网络没问题，那就看认证环节。执行：
   ```console
   $ ssh -vT git@gitee.com
   ```
   在调试输出里看到关键一步：SSH 确实连上了服务器，服务器也发来了认证请求，
   但客户端**没有一把服务器认可的密钥**，所有尝试的密钥都被拒，最后报 `Permission denied (publickey)`。

**结论**：`Permission denied (publickey)` 不是「连不上」，而是「连上了，但服务器不认识你」。
这两件事报错很像，但原因完全不同。这个区分是解开问题的关键。

### 根本原因

本机 `~/.ssh/` 下确实有一对密钥（`id_rsa` / `id_rsa.pub`），
但**这把公钥只加到了 GitHub 账号，没有加到 Gitee 账号**。

所以：

- 连 GitHub → 服务器认识这把钥匙 → 通过 ✅
- 连 Gitee → 服务器没见过这把钥匙 → 拒绝 ❌

公钥就是一把锁的钥匙，**在哪个平台上用，就要把公钥复制到哪个平台的账号设置里**。
一把钥匙只能开它登记过的门，换一个平台要重新登记一次。这一步我一开始漏了。

### 怎么解决的

验证了这个判断：对 GitHub 执行同样的命令，直接认出身份：

```console
$ ssh -T git@gitee.com
git@gitee.com: Permission denied (publickey).

$ ssh -T git@github.com
Hi Archer-redA! You've successfully authenticated, but GitHub does not provide shell access.
```

同一把密钥、同一台机器，**GitHub 通过而 Gitee 拒绝**，直接印证了「公钥没在 Gitee 登记」这个结论。

解决路径有两条：

- **方案 A（采用）**：改用 GitHub 托管本仓库 —— 密钥已经登记好，认证一次通过，不再折腾。
  项目仓库地址：<https://github.com/Archer-redA/from-code-to-physical>
- **方案 B（备选，如果之后需要 Gitee）**：把公钥内容
  （`cat ~/.ssh/id_rsa.pub` 的输出）完整复制，粘到 Gitee 的
  「设置 → 安全设置 → SSH 公钥」里保存，之后 `ssh -T git@gitee.com` 就会返回成功提示。

### 学到的

**看到 `Permission denied` 先别急着怀疑网络，先分清是「连不上」还是「不被认识」。**
用 `ssh -T` 测一下目标平台的认证状态，几秒钟就能定位，
比在代理和防火墙设置里绕半天有效得多。

## 坑 2：SSH 的 22 端口不通，改用 443 端口

**现象**：按默认方式连 GitHub 时，SSH 连接超时、卡住不动。

**原因**：GitHub 的标准 SSH 端口是 22，但在国内网络环境下这个端口经常被阻断。

**解决**：GitHub 官方提供了备用入口 `ssh.github.com:443`，把 SSH 流量伪装成 HTTPS 流量出去。
在 `~/.ssh/config` 里加上：

```
Host github.com
    Hostname ssh.github.com
    Port 443
    User git
```

这样执行 `git push` 时，SSH 会自动走 443 端口，绕过对 22 端口的限制。
配置写一次就一劳永逸，之后所有 GitHub 的操作都自动走这条路。

**这个坑的价值**：它解释了为什么「配好了密钥却还是连不上」——
密钥对但端口不通，同样推不上去。认证（钥匙对不对）和连通（路通不通）是两个独立的问题，
排查时要分开验证。

## 一句话总结

**卡得最久的是 Gitee 的 `Permission denied (publickey)`：一直以为是网络问题，
最后发现是公钥只加到了 GitHub、没加到 Gitee；用 `ssh -T` 测出两边结果不同才定位到原因。
解决方案是改用 GitHub（密钥已登记），备选方案是把公钥补加到 Gitee。**
